# 方案简化

在当前讨论中使用这套审查方法，按任务规模合并步骤。其他任务沿用原任务约定；这份 skill 不增加平台模式或固定成员角色。

## 核对范围与现状

1. 从当前用户请求区分目标、固定约束、选择偏好和交付要求。“尽量复用、最小改动”是选择偏好，需求覆盖、兼容与安全约束仍须满足。完成条件：后续建议能对应当前请求，关键缺失信息明确标为待确认。
2. 使用已提供的材料，或本轮允许的只读工具核对可复用能力。关注现有 module 的 interface、行为、限制及调用方需要知道的配置；引用已见消息 ID、文件路径与快照哈希。区分“已核对可复用”和“推测可能可复用”。完成条件：影响推荐的每项复用判断都有来源或明确的未验证标记。材料不足时给出有条件的建议与最小核对清单。

## 提出与审查候选

3. 先判断现状是否已满足需求；满足时允许推荐不改动。存在缺口时依次考虑直接复用、现有实现的局部修改，再考虑新增能力，只展开有实际区别的选择。每项必要改动说明所填补的缺口、影响范围和验证办法；每项新增依赖、module 或抽象说明已有能力不足的具体原因。完成条件：推荐覆盖需求，每项新增成本都有必要性依据。
4. 结合其他成员的公开依据审查同一候选：哪些部分可以删除，复用是否需要额外配置、特殊分支或过多内部知识，局部修改是否遗漏调用方与兼容行为。比较整体维护负担和影响范围，代码行数仅作辅助；更少代码但更多耦合的做法可能更复杂。修改候选时说明相对上一版的增删及理由，按平台约定提交完整候选。完成条件：判断指向当前候选，修订有具体缺口与依据，不因成员赞同而把未验证判断写成事实。

## 交付

按用户要求的篇幅与格式给出推荐、复用依据、必要改动和验证方式，标明未确认事项及仍有依据的分歧；无需把所有审查步骤写成章节。只要求比较或讨论时，交付分析即可。平台只读讨论中的“改动”是建议清单，实际修改与验证结果须有真实执行依据。

完成条件：结果回应本轮请求、满足固定约束、解释必要复杂度，并保留不确定性。沿用平台的回答格式、候选版本和投票规则；skill 不扩大执行权限或读取他人私有 memo。
